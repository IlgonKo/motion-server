# TD-044 CPX 0x27F1 파라미터 저장 API 의미 정합성

## 현재 상태

- 등록일: 2026-11-26
- 상태: `open` (구현 보류)
- 재개 시점: Soft ESC 마무리 후 추가 논의·계약 확정을 거쳐 구현한다.
- 관련 작업: [RF-003](../rf/RF-003-bus-io-management.md).

## 문제와 근거

제조사 설명과 현재 Motion Server의 `system/io/param_storage` 명칭·의미가 다르다.
근거는 저장소 [CPX-AP-I-EC-M12 매뉴얼](../../../Reference/CPX-AP-I-EC-M12.pdf),
2025-05d, 22페이지 표 19 `Stored Parameter NV (0x27F1)`이다.
`0x27F1:01`은 UNSIGNED8, rw이며 이름은 Mode이다.

| 값 | 제조사 설명 | 현재 서버 해석/구현 |
| --- | --- | --- |
| 0 | 저장된 파라미터 삭제, 현재 파라미터 변경 없음 | `mode="volatile"` → 0 쓰기. 휘발성 저장 대상 선택으로 설명 |
| 1 | 파라미터 저장 또는 기존 저장 파라미터 갱신 | `mode="non_volatile"` → 1 쓰기. 비휘발성 저장 대상 선택으로 설명 |
| 2 | 저장 데이터 삭제 및 파라미터 기본값 복원 | 현재 API에서 허용하지 않음 |

현재 `device/cpx_ap_i_ec/profile.py`의 `set_io_parameter_storage()`는 위 0/1을
SDO로 쓰고 반환한다. 지속적인 자동 저장 동작을 서버에서 구현하지 않으며 별도 결과 readback도 없다.
따라서 문제는 SDO 주소나 정수 매핑 자체보다 API·UI·문서가 쓰기에 부여한 의미에 있다.

`volatile` 요청은 단순히 앞으로의 저장 방식을 바꾸는 것이 아니라 저장 데이터를 삭제할 수 있다.
`non_volatile`도 이후 모든 파라미터 변경을 자동 저장한다는 근거가 매뉴얼에 없다.
RF-003에서 확인한 실장치 SDO 쓰기 성공은 이 의미나 재기동 후 보존 정책까지 검증한 것이 아니다.
Mode라는 필드명만으로 지속적인 저장 모드로 해석한 기존 계약을 수정해야 한다.

## 수정 방향 (세부 API는 미확정)

- 제조사 동작인 저장/갱신, 저장 데이터 삭제, 기본값 복원을 명확히 구분한다.
- 기존 `volatile/non_volatile` 명칭을 자동 저장 정책으로 설명하지 않는다.
- API 이름·인수, capability/메서드, Schema, IO Control Panel, 공식 client/예제,
  문서를 확정한 의미로 함께 정리한다. 이전 계약 유지용 alias/fallback은 기본 범위에 넣지 않는다.
- 저장 데이터 삭제와 기본값 복원은 서로 다른 동작이며 암묵적으로 실행하지 않는다.
- Soft ESC는 기존 서버 명칭을 제조사 동작의 근거로 삼지 않는다. FMU 내부를 서버가 직접
  처리하지 않고 장치 OD 계약을 통해 요청하는 책임 경계를 유지한다.
- 이 TD 등록으로 Mode=2 지원이나 RF-017의 가상 CPX 영구 저장을 승인하지 않는다.

## 추가 논의할 사항

1. 공개 API를 저장 명령과 삭제 명령으로 나눌지, 명시적인 operation 인수로 구성할지 결정한다.
   `param_save` 재사용 여부를 포함하며 아직 이름을 확정하지 않는다.
2. Mode=0 저장 데이터 삭제를 공개 API에 제공할지, 권한·실행 조건·UI 표현을 어떻게 할지 정한다.
3. Mode=2 기본값 복원을 이번 범위에 포함할지 별도 작업으로 남길지 정한다.
4. 저장 대상이 station/AP module/IO-Link 중 어디까지인지, 현재값과 재기동 시 복원에 미치는 영향을
   해당 펌웨어·매뉴얼과 시험으로 확인한다. 명칭만으로 AP/IOL 전체 저장을 가정하지 않는다.
5. API Success를 SDO 쓰기 수락으로 유지할지와 저장 완료 확인 가능성을 논의한다.
   `:02 Loaded`는 startup 복원 성공 표시, `:03 Used Memory`는 사용량이므로 저장 완료 신호로 단정하지 않는다.
6. 짧은 간격의 연속 요청 거부 및 처리 시간의 의미를 검증한다.
   기존 `0x08000000`은 일반 오류이며 그 코드만으로 busy를 확정하거나 자동 재시도하지 않는다.
7. 저장 후 값 변경·재기동, 저장 데이터 삭제 후 현재값 유지·재기동 등 의미 검증 시나리오와
   Soft ESC/실 CPX 비교 범위를 확정한다. 삭제/복원 시험은 시험 장치·데이터로 수행한다.

## 제외 범위

- Soft ESC 마무리 전 서버 코드/API/실장비 변경.
- 모듈 진단 및 DI/AI 유효성(TD-043/RF-012).
- 실장비 snapshot/장치 간 파라미터 이전 및 RF-017 저장소의 임의 확장.
- 별도 사용자 지시 없는 Node-RED 시험. 후속 계약 변경 시 예제 수정 범위와 시험 허용 여부를 구분한다.

## 완료 조건

- 제조사 동작과 API 이름·인수·응답 의미의 대응표가 확정되고 문서화된다.
- 저장 대상 선택으로 오해하는 명칭과 설명이 코드·Schema·화면·공식 예제에서 정리된다.
- 저장/갱신과 저장 데이터 삭제의 현재값·재기동 동작을 구분하여 검증한다.
- 기본값 복원은 확정한 지원/제외 정책대로 처리되고 의도하지 않은 삭제가 발생하지 않는다.
- authority, unsupported, 장치 거부 및 연속 요청 실패가 기존 API Fail 계약을 유지한다.
- 실장치/Soft ESC 의미 검증과 미검증 범위를 기록하고 RF-003의 과거 해석을 정정한다.
