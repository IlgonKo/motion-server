# TD-043 일반 DI/AI 입력 유효성 전달 및 CPX 진단 연계

## 현재 상태

- 등록일: 2026-11-26
- 상태: `open` (구현 보류)
- 재개 시점: Soft ESC 작업 마무리 후 추가 논의와 계약 확정을 거쳐 진행한다.
- 관련 결정/기능: DEC-020, [RF-012](../rf/RF-012-cpx-ap-optional-diagnostic.md).

## 문제와 배경

EtherCAT 통신과 WKC가 정상이더라도 장치 내부에서 입력 갱신이 실패할 수 있다.
현재 일반 DI/AI API는 값 목록만 제공하므로 마지막 수신값과 유효성이 확인된 입력을
구분해 전달하지 못한다. 같은 값이 반복된다는 사실만으로 갱신 중단을 판정할 수도 없다.

현재 CPX 매핑 검증은 추가 Diagnosis TxPDO를 수용하지 않으며 RuntimeDiagnosticMonitor는
CPX 진단을 자동 수집하지 않는다. 저장소 ESI의 `0x1AF1`은 `0x6102:01~04`의
Category Status(32 bit), 활성 건수(16 bit), 최신 진단 모듈(16 bit), 최신 코드(32 bit)로
총 12바이트를 정의한다. 이는 전체 활성 모듈 장애 목록이나 입력 최신성 보장을 뜻하지 않는다.

## 확정한 책임 경계와 공개 계약 방향

- Soft ESC는 장치 내부의 문제를 외부에서 해석 가능한 CPX 진단 데이터로 제공한다.
  Motion Server는 이를 수집·해석하여 API와 화면에 전달하며 FMU 내부를 직접 알지 않는다.
- 일반 DI/AI 유효성은 **모듈 단위**로 판단하고 해당 모듈의 모든 입력에 공통 적용한다.
  채널 단위 판정은 제외한다.
- 마지막 수신값은 유지하고 유효성을 값과 분리하여 전달한다.
- 상태 의미는 `valid`(확정된 기준 만족), `invalid`(입력에 영향을 주는 장애 확인),
  `unknown`(진단 미지원·미수집·판정 근거 부족)으로 구분한다. 실제 API 필드/배치는 미확정이다.
- Diagnostic source는 기존 합의대로 station 단위 `IO`를 사용한다.
  문제 모듈은 상세정보이며 독립 module/channel Diagnostic source를 만들지 않는다.
- 진단이 없거나 수집되지 않았다는 이유만으로 정상으로 간주하지 않는다.
  최신 진단에 언급되지 않은 모듈을 모두 valid로 추정하지 않는다.
- 현재 입력 유효성과 Ack 대기로 남아 있는 Diagnostic 이력은 분리한다.

## RF-012와 구현 범위 구분

- RF-012: 선택형 `0x1AF1` 활성화, assignment/mapping readback 검증,
  12바이트 진단 영역 및 모듈 데이터 offset 처리, `0x6102` 해석과 station Alarm/Fault 생성.
- TD-043: 위 진단 근거를 이용한 모듈별 일반 DI/AI 유효성 계약, API Schema/응답,
  클라이언트 표시 및 회귀 검증. 진단 수집 구현을 TD에 중복 정의하지 않는다.
- DEC-020의 명시적 health source 원칙을 유지한다. 진단 PDO는 선택형이며 자동 추가하지 않는다.
- SDO polling은 현재 승인된 범위가 아니다. 필요할 경우 별도 접근·부하·실패 정책을 먼저 논의한다.
- 내부 구현 메서드와 데이터 모델은 재개 시 확정한다. 이번 등록으로 새 API나 capability를 추가하지 않는다.

## 재개 시 추가 논의할 사항

1. **모듈별 판정 근거:** 최신 모듈/코드만 제공되는 상황에서 복수 모듈 장애와 개별 복구를
   어떻게 확인할지 결정한다. 정보가 부족하면 unknown으로 남기며 정상이라고 추정하지 않는다.
2. **진단별 입력 영향:** 입력 무효를 뜻하는 코드/상태와 단순 경고·출력 문제를 구분한다.
   모든 station Alarm/Fault를 전체 모듈 invalid로 변환하지 않는다.
3. **갱신 실패 표현:** Soft ESC가 입력 갱신 실패를 어떤 CPX 진단으로 알리고 해제하는지,
   실제 CPX에서도 동일하게 해석 가능한 근거가 무엇인지 확인한다. 별도 최신성 정보가 필요한지 검토한다.
4. **상태 전환:** 최초 수신 전, 진단 비활성/미지원, 진단 데이터 누락, Bus 단절, reconnect,
   장애 해제 시 valid/invalid/unknown 기준과 마지막 값 유지 정책을 확정한다.
5. **API/화면:** 모듈별 상태와 사유의 필드 위치, 평탄화된 DI/AI 목록과 모듈 간 대응,
   조회/feedback 일관성 및 IO Control Panel 표시를 결정한다.
6. **Diagnostic lifecycle:** Alarm/Fault 변환, latching·resolve와 입력 유효성 복구의 관계를
   RF-012에서 확정하고 기존 reset/Ack 계약과 충돌하지 않는지 검토한다.
7. **검증 대상:** 실 CPX, Virtual CPX, Soft ESC의 역할과 시험 fixture를 확정한다.
   Node-RED 시험은 별도 사용자 지시 전까지 실행하지 않는다.

## 제외 범위

- 채널별 유효성 및 module/channel 독립 Diagnostic source.
- FMU 내부 상태 직접 조회, WKC만으로 특정 모듈 장애 추정.
- 값 변화량만으로 최신성 판단, 단발 AP/ISDU 요청 실패를 지속 Diagnostic으로 승격.
- 이번 문서 등록에 따른 코드 수정, 실장비 시험 또는 1.0 태그 변경.

## 완료 조건

- RF-012의 선택형 진단 수집과 연계되어 모듈별 유효성 판단 근거 및 한계가 문서화된다.
- 일반 DI/AI 마지막 값과 모듈 유효성이 API Schema·응답·화면에서 구분된다.
- WKC 정상/입력 갱신 실패, 정상적으로 동일 값 유지, 복수 모듈 장애·개별 복구,
  진단 비활성·미지원·미수집 및 Bus 단절/reconnect를 검증한다.
- 근거가 부족한 모듈을 valid로 표시하지 않고, 영향 없는 모듈을 임의로 invalid로 만들지 않는다.
- 조건 해제와 Diagnostic Ack 대기를 구분하고 유효성 복구 정책을 검증한다.
- 진단 PDO 활성/비활성 시 매핑·offset 및 기존 I/O 값 해석 회귀와 real/mock 공개 계약을 검증한다.
