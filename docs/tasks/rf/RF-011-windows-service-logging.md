# RF-011 Windows Service 실행 및 파일 로그 옵션

- 상태: `planned` (설계 논의 중, 구현 미착수)
- 1차 정책 확정: 2026-11-24

## 확정 정책 — 2026-11-24

### Windows Manager 책임 경계 — 추가 확정

- Motion Server Windows Manager를 서버와 별도로 두고 콘솔/서비스 실행 모드 선택 및 모드별 운영 설정을 담당하게 한다.
- Motion Server 자체에 Windows 서비스 진입점이나 Windows 서비스 종속 코드를 추가하지 않는다. Linux Docker와 Windows에서 공통 서버 실행 계약을 유지한다.
- Manager는 서버 executable 위치, 실행 상태, 서비스 등록·자동 시작·시작/중지·장애 재시작 정책을 관리한다. 선택한 executable의 기존 패키지 config.txt를 사용하며 별도 설정 파일 선택 기능은 추가하지 않는다.
- 콘솔 모드에서는 콘솔 창에서 서버를 실행한다. 서비스 모드에서는 Windows 서비스로 실행을 관리한다. Manager는 로그 설정을 변경하지 않는다.
- 모션·장치 설정의 원본은 기존 config.txt다. 서비스 전용 장치 설정은 만들지 않는다.
- 모드 전환은 기존 실행을 종료한 뒤 선택한 모드로 실행하며 중복 기동을 방지한다.
- 파일 로그는 실행 모드와 독립된 공통 서버 선택 기능이다. 콘솔/서비스 모두 파일 기록을 끈 상태로 실행할 수 있다.
- 로그 설정은 .env/config.txt에서 사용자가 관리한다. Manager는 config.txt를 수정하거나 로그 활성화 여부를 기동 조건으로 검사하지 않는다. Manager 설정에도 로그 항목을 중복 저장하지 않는다.
- Manager 설정 저장 형식·위치는 아래 확정 정책을 따른다. 정상 종료 신호와 서버 Restart 후 프로세스 추적 방법은 구현 검토 대상으로 남긴다.
- 별도 Host 직접 구현, 서버 내부 서비스 진입점, 기존 wrapper 활용을 비교한 뒤 위 책임 경계로 정리했다. pywin32 채택 및 LocalSystem 계정은 아직 확정하지 않았다.

### Windows Manager GUI — 확정

- 작은 GUI를 제공한다. 서버 실행 경로, 콘솔/서비스 모드 선택, 시작/중지/재시작, 서비스 등록/제거와 부팅 자동 시작 설정을 제공한다.
- 상태는 중지·시작 중·실행 중·종료 중·실행 실패 등 프로세스/서비스 실행 상태까지만 표시한다. 축·Bus·Diagnostic은 기존 Control Panel에서 확인한다.
- Stop 버튼은 Motion Server를 종료하며 Manager GUI는 유지한다. Manager 창을 닫는 동작은 Stop과 다르며 실행 중인 서버는 유지한다.
- 콘솔 모드에서는 관리 중인 서버에 종료를 요청한다. 서비스 모드에서는 서비스 중지를 요청하여 서버를 종료한다. 정상 종료 대기와 제한 시간은 아래 공통 정책을 따른다.
- 모션·장치·로그 설정 편집 기능은 제공하지 않는다.
- 실행 중 모드 변경은 즉시 적용하지 않고 기존 실행을 종료한 뒤 전환한다.
- 창을 다시 열었을 때 기존 실행을 식별하는 방법과 Manager 자체의 GUI/서비스 내부 구성은 구현 전 후속 논의로 확정한다.

### Manager 설정 및 관리 대상 — 확정

- 1차 관리 대상은 서버 인스턴스 하나다. 사용자가 motion_server.exe를 선택한다.
- 서버는 기존 패키지 config.txt를 사용하며 Manager는 이를 편집하거나 별도 복사본을 생성하지 않는다.
- Manager 설정은 `%ProgramData%\MotionServer\windows_manager.json`에 저장한다. 서버 실행 경로·선택한 실행 모드·서비스 자동 시작 여부를 보관한다.
- 재시작 정책은 합의한 내부 기본값을 사용하며 1차 GUI에서 세부 수치 편집을 제공하지 않는다.
- GUI 재실행 시 설정을 읽고 실제 프로세스/서비스 상태를 다시 확인한다. 저장된 실행 상태를 사실로 간주하지 않는다.
- Manager가 실행한 서버만 관리한다. 사용자가 직접 실행한 서버를 임의로 종료하거나 편입하지 않으며 기동 충돌 시 원인을 표시한다.
- 프로세스 식별/소유권 유지와 정상 종료·Restart 추적의 구체적인 구현은 다음 논의에서 확정한다.

### 공통 실행 정책

- 파일 로그 기능과 Windows 서비스 실행을 분리한다. 파일 로그는 콘솔 실행에서도 사용한다.
- 기존 콘솔 실행을 유지하며 서비스는 사용자가 명시적으로 설치하는 선택 기능이다.
- 콘솔과 서비스는 같은 executable 및 config.txt를 사용한다. 서비스 전용 장치 설정을 만들지 않는다.
- 서비스는 서버의 실행·종료를 관리한다. install/uninstall/start/stop/restart/status를 제공한다.
- 부팅 자동 시작은 설치 시 선택하며 기본은 자동 시작이다.
- 서비스 stop은 서버의 기존 정상 종료 경로로 전달한다. 정리 시간을 보장하고 제한 시간을 넘으면 강제 종료한다.
- 장애 재시작은 프로세스 비정상 종료에 한해 제한적으로 수행한다. Bus Fault나 초기화 실패 상태로 서버가 살아 있으면 자동 재시작하지 않는다.
- system/server/restart는 서비스 실행 중에도 서버 재실행으로 이어지며 서비스 stop과 구분한다.

### 종료 및 장애 재시작 수치 — 확정

- 정상 종료는 최대 30초 동안 장치·연결·저장 worker·로그 정리를 기다린다.
- 제한 시간 초과 시 원인을 기록하고 강제 종료한다. Manager Stop 버튼 또는 서비스 Stop 요청으로 종료한 경우 자동 재시작하지 않는다.
- 프로세스 비정상 종료 후에는 5초 간격으로 최대 3회 재시작한다. 3회 재시작 후에도 실패하면 중지 상태로 유지하며 수동 시작이 필요하다.
- 프로세스가 30분 연속 실행되면 장애 재시작 횟수를 초기화한다. 장치 정상 여부가 아닌 프로세스 생존 기준이다.
- Bus Fault나 초기화 실패 상태로 프로세스가 살아 있는 경우 자동 재시작하지 않는 기존 합의를 유지한다.
- system/server/restart는 사용자 요청 재시작이므로 장애 횟수에 포함하지 않는다.
- 서비스 Stop과 Restart가 동시에 발생하면 Stop을 우선하며 종료 후 다시 실행하지 않는다.
- 위 값은 서비스 관리 정책으로 두며 모션·장치 설정과 분리한다. 구체적인 서비스 구현 도구와 종료 신호 전달 방법은 후속 논의에서 확정한다.

### 파일 로그

- 시작·종료, 초기화 실패, 연결·제어권, 명령 실패, Fault 및 복구를 기록한다.
- 정상 명령·상태 로그의 기록 여부는 기존 활성화 설정을 따른다.
- 전용 worker에서 파일을 기록한다. 버스 주기에서 파일 write/flush를 기다리지 않는다.
- 설치 폴더와 분리된 저장 경로를 설정하며 파일 기록만 추가 옵션으로 활성화한다.
- 콘솔 실행에서는 기존 기능별 로그 설정으로 활성화된 로그를 항상 콘솔에 출력한다. 별도의 `MOTION_SERVER_LOG_CONSOLE_ENABLED` 설정은 만들지 않는다.
- 콘솔 실행에서 파일 기록을 켜면 콘솔과 파일 양쪽에 기록한다. 서비스 실행은 콘솔 창 없이 동작하며, 파일 기록은 활성화한 경우에만 수행한다.
- 시간·로그 수준·내용을 포함한 일반 텍스트를 사용한다.
- 크기 기준 rotation을 사용한다. 기본은 파일당 10 MB, 이전 파일 10개 보존이다.

### 실패 처리

- 파일 로그는 콘솔/서비스 모두 선택 기능이다. 서비스 모드에만 로그 기동 조건을 추가하지 않는다.
- 활성화된 파일 로그의 초기 열기 실패와 운전 중 디스크 부족/쓰기 실패 모두 Motion Server 실행을 중단하지 않는다. 사용 가능한 진단 경로로 알리고 아래 비동기 재시도 정책을 동일하게 적용한다. 콘솔 모드에서는 콘솔에 오류를 표시한다.
- Windows Event Log는 확정된 알림 경로가 아니다. 서비스 모드의 오류 알림 경로는 Manager 구현 검토에서 다루며 공통 서버에 Windows 종속 기능을 추가하지 않는다.
- 로그 대기열이 포화되면 버스 처리를 기다리게 하지 않고 가장 오래된 로그부터 버린다. 유실 개수를 집계해 기록 가능해지면 알린다.

### 남은 구현 검토 사항

- 확정한 정상 종료/Restart API/비정상 종료 정책을 구현할 신호 전달 및 식별 방법.
- 서비스 구현 도구·실행 계정·설치/관리 명령 형태.
- GUI와 백그라운드 관리 기능 사이의 상태 조회/조작 및 프로세스 소유권 유지 방법. 설정 저장 위치·관리 대상 범위는 확정했다.
- 서비스 모드에서 파일 로그 실패 등을 알릴 수 있는 진단 경로와 Manager 책임 경계.
- 숨겨진 콘솔과 Job Object는 검토 후보일 뿐 확정된 구현 방식이 아니다. 기존 정상 종료 경로 및 Restart 이후 관리가 가능한지 확인한 뒤 구체안을 제시한다.
- 사용자 기능·설정·로그 실패 정책은 위 확정 사항을 따른다. 위 구현 검토가 서버 역할이나 공개 계약 확장을 요구하면 구현 전에 별도로 논의한다. 현재 합의는 서비스 설치나 코드 구현 착수를 의미하지 않는다.

### 비동기 로그 세부 정책 — 확정

- 대기열은 최대 10,000건이며 포화 시 가장 오래된 로그부터 버리고 유실 건수를 집계한다.
- 초기 파일 열기 또는 파일 쓰기 실패 시 worker에서 5초 간격으로 파일을 다시 연다. 실패 중 새 로그도 제한된 대기열에 보관하며 같은 포화 정책을 적용한다.
- 최초 실패를 알리고 동일 오류가 지속되면 60초마다 최대 1회 알린다. 복구 시 복구 사실과 누적 유실 건수를 파일에 기록한다.
- 종료 시 남은 로그 기록을 최대 3초 기다린다. 이는 전체 정상 종료 제한 30초 안에 포함하며 별도로 연장하지 않는다.
- 종료 대기 초과 시 남은 로그 수를 가능한 진단 경로에 알리고 종료를 진행한다.
- 파일 쓰기·재시도·오류 알림은 worker에서 처리하며 버스 주기가 기다리지 않도록 한다.
- 위 수치들은 내부 기본값으로 둔다. 사용자 설정은 파일 활성화·경로·파일 크기·보존 개수만 노출한다. 별도 전역 로그 수준 설정은 추가하지 않고 기존 기능별 로그 활성화 정책을 유지한다.

### 파일 설정 및 기동 조건 — 확정

```ini
MOTION_SERVER_LOG_FILE_ENABLED=0
MOTION_SERVER_LOG_FILE_PATH=
MOTION_SERVER_LOG_FILE_MAX_BYTES=10485760
MOTION_SERVER_LOG_FILE_BACKUP_COUNT=10
```

- 파일 기록 활성화 시 경로는 필수다. 절대 경로 또는 메인 설정 파일 위치 기준 상대 경로를 사용한다.
- 부모 폴더가 없으면 자동 생성한다. 지정 파일을 현재 로그로 쓰고 이전 파일은 `.1`부터 `.10`까지 보관한다(기본 보존 개수 기준).
- 재기동 시 기존 파일에 이어 쓰고 크기 제한 도달 시 순환한다.
- 서버 인스턴스마다 별도 파일을 사용한다. 같은 파일의 중복 사용은 거부한다.
- 콘솔/서비스 모두 파일 기록은 선택 사항이며 비활성화 상태에서도 실행할 수 있다. 비활성화 상태에서는 파일 경로를 요구하지 않는다.
- 초기 파일 열기 실패 시에도 서버 실행을 유지하고 오류 알림·비동기 재시도를 수행한다. 콘솔/서비스에 동일하게 적용하며 Manager는 로그 설정이나 파일 열기 가능 여부로 기동을 제한하지 않는다.
- 별도 전역 로그 수준 설정은 만들지 않고 기존 기능별 로그 활성화 설정을 유지한다.

## 사용자 가치

Windows EtherCAT host에서 사용자 로그인이나 열린 terminal 없이 Motion Server를 자동 실행하고,
startup·runtime·fault 기록을 파일로 보존해 운영 및 장애 분석에 사용할 수 있게 한다.

## 실행 모드

- 기존 foreground/console 실행은 개발, 설정 확인과 수동 진단 용도로 유지한다.
- Windows Service 실행은 설치 시 사용자가 선택할 수 있는 운영 옵션으로 제공한다.
- 두 실행 모드는 동일한 executable, configuration schema와 device catalog를 사용한다.

## Service 구현 범위

- service install/uninstall과 start/stop/restart/status 명령을 제공한다.
- Windows boot 시 자동 시작 여부를 선택할 수 있게 한다. 장애 재시작은 위 확정한 내부 기본값을 적용하며 1차 GUI에서 세부 수치를 편집하지 않는다.
- stop/shutdown 요청에서 EtherCAT output과 runtime resource를 안전하게 정리한다.
- service account, working directory, configuration/catalog 경로와 권한 요구사항을 문서화한다.
- 이미 실행 중인 foreground instance 또는 동일 TCP port와 충돌할 때 명확한 오류를 제공한다.

## 파일 로그 범위

- 기존 기능별 로그 활성화 설정을 유지하고 file output의 활성 여부를 추가한다. 콘솔 출력용 별도 enable 설정은 제공하지 않는다.
- 별도 전역 로그 수준 설정은 추가하지 않는다. 파일 설정 키와 경로/파일명은 위 확정 정책을 따른다.
- size 기반 rotation과 이전 파일 개수 기준 retention을 설정한다. 기본은 10 MB 및 이전 파일 10개다.
- initialization error, connection, authority, command rejection, EtherCAT fault와 recovery를 보존한다.
- log directory 생성/쓰기 실패에 대한 공통 서버 정책과 사용 가능한 오류 진단 경로를 정의한다. Windows 전용 진단 연동 경계는 후속 논의에서 확정한다.
- password, token 또는 불필요한 전체 environment 값은 기록하지 않는다.

## Packaging 및 Migration

- Windows standalone package에 service 관리 도구와 필요한 runtime dependency를 포함한다.
- 설치 경로 변경은 [TD-019](../td/TD-019-project-path-migration.md), legacy service 식별자 migration은
  [TD-020](../td/TD-020-legacy-runtime-identifiers.md)과 조율한다.
- 설치 및 사용자 문서 반영은 [RF-006](RF-006-deployment-validation.md)과
  [RF-010](RF-010-user-documentation.md)의 검증 범위에 포함한다.

## 검증 계획

- clean Windows PC에서 install/start/status/restart/stop/uninstall lifecycle을 검증한다.
- Windows 재부팅 후 자동 시작과 Motion Server TCP 연결을 확인한다.
- 정상 종료, initialization failure, process crash와 configured recovery 동작을 검증한다.
- log rotation/retention, 동시 write, disk/write failure와 restart 후 로그 연속성을 검증한다.
- foreground와 service mode가 동일 설정에서 같은 axis/I/O 구성을 생성하는지 비교한다.

## 완료 증거

완료 시 service lifecycle 기록, configuration 표, packaging manifest, 대표 log와 clean-system 시험 결과를 추가한다.

- 아래는 RF-017 완료 직후 설계 논의를 시작하기 전의 점검 기록이다. 현재 정책은 위 확정 사항을 따르며 당시 검토 과제를 미결정 사항으로 다시 취급하지 않는다.
