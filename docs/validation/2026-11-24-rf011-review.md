# RF-011 구현 리뷰 및 검증 기록

- 날짜: 2026-11-24
- 범위: 파일 로그, Windows 서비스 등록, 패키징 및 사용 안내
- 결과: 리뷰 수정 및 자동 시험 통과. 실제 SCM/LocalSystem 기본 13개 및 추가 12개 검사 통과. 재부팅은 사용자 지시로 제외. 실제 장비 동작 인수와 TD-042는 별도 범위.

## 리뷰 결과

등록 스크립트는 관리자 권한과 패키지를 먼저 확인한다. 실행 또는 전환 중인 동명 서비스는
수동 중지를 안내하며, 중지된 서비스만 삭제하고 기본값으로 재등록한다. Start/Stop 호출은 없다.
파일 로그의 열기·쓰기·rotation 실패는 비동기 writer에서 재시도하며 서버 종료로 전파하지 않는다.

대기열 포화 시 기록 중인 항목까지 유실로 집계할 수 있는 문제를 발견했다. 기록할 항목을
대기열에서 먼저 꺼내도록 수정했다. 쓰기 실패 시 여유가 있으면 다시 넣고, 대기열이 가득
찼으면 실패한 가장 오래된 항목을 유실로 집계한다. 성공적으로 기록한 항목은 유실로 세지 않는다.
진행 중 쓰기를 멈춘 상태에서 대기열을 채우는 재현 테스트를 추가했다.

## 자동 검증

수정 후 다음 테스트 29개가 통과했다.

```text
python -B -m unittest tests.test_file_logging tests.test_windows_service tests.test_motion_server_application tests.test_runtime_logging tests.test_error_contract_static
```

- 서비스 테스트는 Windows 서비스 명령을 대체한 테스트이며 실제 서비스를 등록하지 않는다.
- 이전 전체 단위/Mock 회귀 622개 통과 기록은 이번 수정 전 결과다.
- 이전 패키지의 WinSW testwait 시험에서 Mock 기동, 로그 기록, 정상 종료 및 listener 해제를 확인했다.
- 위 시험은 SCM/LocalSystem 시험이 아니다. 이번 수정 후 EXE 재빌드는 수행하지 않았다.
- 운영 서버, 실제 EtherCAT 장치, Node-RED는 조작하거나 시험하지 않았다.

## 남은 인수 및 제약

- 실제 패키지 재빌드와 manifest 검증 완료(아래 후속 기록).
- 별도 시험 환경의 신규/교체 서비스 등록 및 수동 시작·중지.
- LocalSystem 파일/Npcap 접근, 재부팅 자동 시작, 장애 복구 기본값 확인.
- 정상 종료 및 30초 제한 시간 이후 강제 종료 확인.
- 기존 `system/server/restart`는 새 프로세스를 만들므로 서비스 연동은 TD-042 이후 검증한다.
- WinSW의 서버 출력 캡처는 비활성이다. 파일 로그 장애의 stderr 알림은 서비스 화면에서
  보이지 않으며, 파일 기록이 복구되면 복구 및 유실 정보를 기록한다. Event Log로 서버 로그를
  전달하는 기능은 구현하지 않았다.

## 실제 SCM/LocalSystem 검증 — 2026-11-24

이 절은 앞의 실제 서비스 미검증 기록 이후 수행한 결과다.

- 시험 서버: Mock 1축, TCP 50485, 시험 패키지 config.txt. 운영 서버/실장비는 사용하지 않았다.
- 신규 등록 후 중지 상태, Automatic/LocalSystem 기본값, 중지된 서비스 교체, 실행 중 재등록 거부를 확인했다.
- 서버 프로세스 PID 37336의 실제 소유자는 NT AUTHORITY\SYSTEM. SCM wrapper PID는 37192였다.
- 설정·카탈로그 읽기와 로그 디렉터리 생성/쓰기 성공. status API는 success, initialized=true, runtime_state=normal이었다.
- Stop 약 0.259초. 이번 실행 로그에 정상 종료 기록, 프로세스 종료 및 포트 해제 확인. 6초 후에도 Stopped.
- 총 13개 검사 통과. 증거: `.codex_output/rf011-scm-result.json`, 시험 패키지 `logs/scm-test.log`.
- 최초 수집기의 JSON 직렬화 지연을 문자열 중심 결과로 바꿔 해결한 뒤 다시 시험했다. 서버 코드는 변경하지 않았다.
- 복구 설정 조회는 5000ms 재시작 2회/86400초 초기화를 확인한 것이며 실제 장애 주입 결과는 아니다.
- 실제 재부팅, 강제 종료 제한 시간, Npcap/영구 저장소 접근과 TD-042는 검증하지 않았다.
- 등록된 서비스는 Automatic/Stopped로 남겨 두었다. 다음 Windows 부팅 시 이 시험 패키지의 Mock 설정으로 실행된다.

## 추가 장애·권한 검증 — 2026-11-24

- 재부팅: 사용자 지시로 skip. 자동 시작 유형 등록 확인만 수행했다.
- LocalSystem 영구 저장: 패키지 Mock 서버에서 0x6083=2233 설정, param_save, 서비스 재기동 후 readback=2233. 시험 DB는 `data/scm-parameters.sqlite`.
- 장애 복구: 시험 서버 자식만 강제 종료. 첫째/둘째 약 7.46/7.66초 후 새 wrapper로 복구하고 정상 API 확인. 셋째는 중지 후 7초 동안 재시작 없음. 설정 5초는 감지와 프로세스 기동을 제외한 Windows 복구 지연이다.
- Npcap: LocalSystem Python 시험 프로세스에서 설치된 PySOEM으로 목록 조회와 기존 설정 NIC open/close 통과. 패키지 실행 파일의 실장비 운전 시험으로 확대 해석하지 않는다. 패킷 교환 및 장치 상태 변경 명령은 실행하지 않았다.
- 종료 제한: 서비스 XML의 실행 대상만 종료 신호를 무시하는 시험 프로그램으로 일시 교체했다. SIGINT 수신 기록 후 30초 제한을 거쳐 강제 종료됨. 중지 명령/SCM 조회 포함 33.75초, PID 15508 잔존 0개.
- 종료 PID 조회 시 PowerShell 종료 코드 1을 시험 스크립트가 오류로 처리했다. 독립 CIM 조회로 부재를 확인하고 시험 판정을 보완했다. 이 도구 문제와 제품 실패를 구분한다.
- 증거: `.codex_output/rf011-remaining-result.json`(12개 검사), `rf011-system-probe.json`, `rf011-probe-signals.txt`.
- 서비스 XML과 config.txt는 원복했고 서비스는 Automatic/Stopped다. 제품 코드를 변경하지 않았다.

## 후속 패키지 검증 — 2026-11-24

- 리뷰 수정 후 Windows 서버 및 3개 Control Panel 실행 파일을 새로 빌드했다.
- 시험 패키지: `.codex_output/rf011-final-package`. 운영 설정을 복사하지 않고 Mock 전용 설정으로 시험했다.
- 서비스 도구, SHA-256, 매뉴얼, 카탈로그 등 패키지 검사: 3,846개 파일, 오류 0개(최초 조립 시점).
- WinSW `testwait`에서 파일 로그 활성/비활성 두 경우 모두 기동, 종료 코드 0, listener 해제를 확인했다.
- 활성 시 Mock 초기화·정상 종료 로그를 확인했고 비활성 시 파일이 생성되지 않았다.
- 시험 스크립트의 초기화 로그 판정 문구가 구버전이어서 첫 판정이 실패했다. 실제 로그의 정상 초기화를 확인하고 판정 문구를 수정한 뒤 두 경우를 다시 실행하여 통과했다. 서버 코드는 변경하지 않았다.
- 증거: `.codex_output/rf011-final-build.log`, `.codex_output/rf011-final-smoke.json`, 시험 패키지의 `artifact-manifest.json`.
- 시험 후 설정·로그까지 포함한 최종 manifest를 다시 생성했다(3,851개 파일, 오류 0개). 이 폴더는 시험용 Mock 설정을 포함한 검증 산출물이다.
- 실제 SCM 등록/LocalSystem·재부팅·장애 복구 인수와 TD-042는 여전히 별도 미완료다. 실제 서비스나 운영 서버는 조작하지 않았다.
